## App fixes found by the poster e2e (parent-decided, parent-implemented)

The worker's poster run failed on all three viewports with two distinct causes:

1. **One-card scrolled out of view (real app bug).** The poster/reduced-motion
   fallback rendered its single chapter card in normal document flow at the top
   of the page while the scroll-track sections below supplied ~28k px of scroll.
   After ~900 px of scrolling the card left the viewport and chapters 1–3 swapped
   content invisibly above it; station navigation scrolled to positions where no
   card existed. Fix: the static one-card now lives in a fixed
   `pointer-events-none` overlay (matching the full-motion pattern) with a
   `pointer-events-auto`, internally scrollable card (`Chapters.tsx`).
2. **Station navigation landed at the wrong scroll position (real app bug, all
   tiers).** `navigateToStation` multiplied the station's PACED progress value
   directly by maxScroll. Station 2 (paced 0.60) landed at raw 0.60, which maps
   back to paced ≈ 0.497 — chapter 1, just under chapter 2's 0.50 start — so
   `aria-current` never set. ScrollRig's deep-link path already converted
   paced→raw via `rawScrollFor()`; `navigateToStation` now does the same
   (`scrollStore.ts`). This also corrects the full-motion TechnicalHUD station
   buttons, which use the same primitive.
3. Harness timing (worker harness, not app): the station-2 native smooth scroll
   (~16k px) exceeded the fixed 1200 ms wait. `verify-poster.mjs` now polls
   until the navigation state settles AND the scroll reaches the expected
   paced→raw target within ±48 px (5 s ceiling). (`poster.log` in this folder
   is the preserved PRE-FIX failure log; the post-fix results are the stdout
   recorded in this report and `poster-results.json`.)

Regression coverage: `staticChapter.test.tsx` pins the fixed-overlay one-card
markup; `scrollStore.test.ts` pins the paced→raw conversion (and that the old
raw multiply is rejected).

## Independent review + remediation (2026-09-28)

Fresh-context reviewer (worker agent "Raman", read-only) audited both fixes and
the evidence. Verdict: fixes mechanically sound, overlay pattern clean, secrets
clean — but NOT APPROVED pending four items, all addressed in a second pass:

1. **Reduced-motion deep links skipped the paced→raw conversion** (the
   module-level DOMContentLoaded listener in `scrollStore.ts` still multiplied
   the paced initial progress by maxScroll; full/lite self-correct via
   ScrollRig, reduced motion never mounts it). Fixed:
   `window.scrollTo(0, max * rawScrollFor(initProg))`. New probe
   `verify-deep-links.mjs` checks `?station=2` lands at raw 0.6818 in BOTH
   poster and reduced-motion tiers.
2. **Wrong arithmetic in comments/report** ("raw 0.60 maps to paced ≈0.44";
   actual `pacedProgress(0.60) = 0.4971` — the conclusion, chapter 1 just
   under chapter 2's 0.50 start, was right; the number was not). Corrected in
   `scrollStore.ts`, `scrollStore.test.ts`, and this report.
3. **Stale poster.log unlabeled** — renamed to `poster-prefail.log`; post-fix
   results live in `poster-results.json` and the refreshed `poster.log`.
4. **Poster harness settled on state, not scroll accuracy** (station 2 was
   recorded at raw 0.624–0.639, below the 0.6818 target). The harness now also
   requires the final scroll within ±48 px of the paced→raw target
   (constants verified against `introTimeline.ts`; the station-3 constant is
   `rawScrollFor(0.85) = 0.8807`, caught and corrected during this pass).

   During remediation the deep-link probe exposed a second layer the reviewer
   could not see from source alone: even with the axis conversion, the listener
   fired before the React tree committed the vh-based track sections, so
   maxScroll was ~0 and no scroll happened. The listener now retries on rAF
   until the tracks exist (bounded ~2 s) before scrolling.
   `debug-deep-link.mjs` documents that diagnosis.
